1. Project Overview
1.1 What Is This Project?
The RBAC (Role-Based Access Control) System is a multi-role, full-stack web application where access to every feature, page, and action is governed entirely by a dynamic permission system. Unlike traditional hard-coded role systems, this platform allows Admins and Managers to configure user access at runtime through a visual permission editor — no developer changes required.

The system is built as a single web application whose interface assembles itself at runtime based on the resolved permission set of the authenticated user.

1.2 The Problem Being Solved
Without This System
With This System
Role access is hard-coded in the codebase
Any user can be granted access to any feature
Adding a new permission requires a developer
Admins and Managers configure permissions via UI
Agents are permanently locked out of certain pages
Agents see exactly what their Manager allows
No visibility into who did what and when
Full audit trail of every action in the system
Managers cannot customise their team's capabilities
No code changes needed to restructure access

1.3 User Roles
The system defines four distinct user roles, each with a specific scope of authority:

Role
Type of User
System Responsibility
Admin
Business Owner / IT Admin
Complete control. Manages all users, assigns managers, configures the entire permission structure, and views full activity overview.
Manager
Team Lead / Department Head
Creates and manages their team (agents and customers). Controls which features each agent can use. Can suspend/ban users within their scope.
Agent
Staff / Operator
Works within modules their Manager has unlocked. Handles leads, tasks, reports — whatever they have been granted access to.
Customer
End Client / User
Accesses their own self-service portal. Views tickets, orders, or interactions. Cannot see internal operations unless explicitly granted.

1.4 Core Architectural Principle
Every page in the application has exactly one required permission atom. If the user holds that atom, the page is accessible. If not, they are redirected to a 403 Forbidden screen. The user's role label alone does not determine access.

⚠ Note: This means a Manager can grant an Agent access to any page — as long as the Manager holds that permission themselves. The system enforces a grant ceiling: you cannot give more than you have.

3.2 Entity Relationships
	•	One user belongs to one role (role_id FK)
	•	One user may have one manager (manager_id self-referencing FK)
	•	Roles have default permissions via role_permissions (many-to-many)
	•	Users have individual permission overrides via user_permissions (many-to-many with granted flag)
	•	Every significant action writes an immutable row to audit_logs

⚠ Note: The resolved permissions for a user = role defaults (role_permissions) merged with individual overrides (user_permissions). When granted=false in user_permissions, the permission is explicitly revoked even if the role grants it.

5. Project Workflow & Architecture
5.1 Request Lifecycle
Every user request passes through the following stages:

Stage
Layer
What Happens
1. Route Request
Browser / Client
User navigates to a URL or performs an action
2. Middleware Check
Next.js middleware.ts (Edge)
Reads JWT from memory, resolves permission atoms, validates the required atom for the route
3. Redirect or Render
Next.js Server
If atom present: renders the page. If not: redirects to /403
4. API Call
Frontend → Backend
Page/component calls the REST API with Bearer JWT in Authorization header
5. Backend Guard
NestJS PermissionGuard
Validates JWT, resolves permissions server-side, checks RequiresPermission decorator
6. Business Logic
NestJS Service Layer
Executes the operation, applies grant ceiling validation for permission changes
7. Audit Log
Audit Interceptor
Writes an immutable audit_log row for every state-changing operation
8. Response
Backend → Frontend
Returns data or error response. Frontend updates UI accordingly

5.2 Dynamic Sidebar Assembly
The sidebar is never hard-coded per role. On login, the frontend resolves the user's full permission set and filters the sidebar navigation items against it. Only items whose required atom is present in the permission set are rendered.

5.3 Permission Resolution Algorithm
Effective permissions for a user are computed as follows:
	•	Start with the default permissions for the user's role (from role_permissions)
	•	Apply user_permissions overrides: if granted=true, add the permission; if granted=false, remove it
	•	The resulting set is the user's effective permissions
	•	This resolved set is returned at login and cached in memory client-side
⚠ Note: Grant Ceiling: When User A tries to grant permission P to User B, the backend must verify that User A holds permission P themselves. If not, the operation is rejected with HTTP 403.

6. Authentication & Authorization Flow
6.1 Login Flow
Step
Action
Details
1
POST /auth/login
Client sends email + password
2
Validate credentials
Backend checks password_hash with bcrypt, verifies account status
3
Issue tokens
Access Token (JWT, 15 min) returned in response body. Refresh Token (JWT, 7 days) set as httpOnly cookie
4

Frontend stores access token in memory (Zustand/React state) — never localStorage
5

6

6.2 Token Refresh Flow
	•	On 401 response: frontend calls POST /auth/refresh with the httpOnly cookie
	•	Backend validates the refresh token, checks it against the session blacklist
	•	Issues new access token, returns in response body
	•	Frontend retries the original request with the new token

6.3 Logout
	•	Client calls POST /auth/logout
	•	Backend adds the refresh token to the session blacklist (in-memory or Redis)
	•	Client clears the access token from memory
	•	httpOnly cookie is cleared by the server

6.4 Security Implementation Details
Concern
Implementation
Brute-force protection
Rate limiting on POST /auth/login (e.g. 5 attempts per 15 minutes per IP)

Access token in JS memory only. Refresh token in httpOnly cookie (not readable by JS)
Session invalidation
Refresh token blacklist checked on every /auth/refresh call
CSRF protection
SameSite=Strict or SameSite=Lax on the refresh token cookie

10. Security Considerations
10.1 Authentication Security
	•	JWT access token stored in JavaScript memory only (never localStorage or sessionStorage)
	•	Refresh token stored in httpOnly, Secure, SameSite=Strict cookie
	•	Access token expiry: 15 minutes. Refresh token expiry: 7 days
	•	Token blacklist for invalidated refresh tokens (Redis recommended for production)
	•	Bcrypt password hashing with minimum 12 salt rounds

10.2 Authorization Security
	•	Every API route validates the user's permission atom server-side via NestJS PermissionGuard
	•	Client-side permission checks (sidebar, disabled buttons) are convenience only — never relied on for security
	•	Grant ceiling enforced server-side on every permission change operation
	•	Manager scope: Managers can only affect users within their own team (enforced via manager_id relationship)

10.3 Input Validation & Protection
	•	All incoming DTOs validated with class-validator in NestJS
	•	SQL injection protection via parameterised queries (TypeORM/Prisma)
	•	XSS protection via React's default output escaping
	•	CORS configured to allow only the frontend origin
	•	Rate limiting on authentication endpoints (minimum 5 req / 15 min per IP)

10.4 Audit Integrity
	•	audit_logs table is append-only — no UPDATE or DELETE operations permitted
	•	Database-level constraints or triggers can enforce immutability
	•	IP address logged with each action for traceability
⚠ Note: Missing from spec: The specification does not define data retention policy for audit logs or GDPR/data deletion requirements. These must be clarified before production deployment.

11. Performance Considerations
11.1 Database
	•	Index users.email (unique, used in every login query)
	•	Index user_permissions.user_id (resolved on every authenticated request)
	•	Index audit_logs.actor_id and audit_logs.created_at (filtered in audit log views)
	•	Index users.manager_id (used in scope-filtering queries)
	•	Use EXPLAIN ANALYZE to profile slow queries before production

11.2 Permission Resolution Caching
	•	Resolved permissions returned at login and cached in client memory
	•	Cache invalidation: re-fetch /auth/me after any permission change affecting the current user
	•	Server-side: consider Redis caching of resolved permission sets with TTL aligned to access token expiry

11.3 Frontend Performance
	•	Next.js Server Components for initial page HTML — reduces client JS bundle
	•	TanStack Query for client-side data caching and stale-while-revalidate patterns
	•	Permission gate components use memoization to prevent unnecessary re-renders
	•	Audit log and user list views must be paginated — never load full datasets
⚠ Note: Missing from spec: No mention of pagination defaults or page size limits. Recommend default page size of 25 with configurable maximum of 100.

	•	401 after failed refresh: clear auth state, redirect to login
	•	403 responses: show permission-denied toast and optionally redirect to /403
	•	Network errors: show retry UI with exponential backoff (TanStack Query handles this)
	•	Form validation: use react-hook-form + zod for client-side validation before API calls

Frontend
	•	React DevTools + Zustand DevTools for inspecting auth and permission state
	•	TanStack Query DevTools for inspecting API cache state
	•	Network tab: all API requests should include the correlation ID for tracing
